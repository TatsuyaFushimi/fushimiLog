1. 全体像 ― 3つの道具の役割分担

この環境は「はじめに」と同じく、作業部屋（Cursor）・現場監督（Claude Code）・職人さん（Codex CLI）の3つでできています。

図1：あなたが話すのは Claude Code だけ。
Claude Code が必要に応じて Codex に仕事を回し、結果を自分で確かめてから報告する
道具たとえ役割
Cursor🏠 作業部屋コードやファイルを開いて見るエディタ。Claude Code の拡張機能を入れて、その画面の中で Claude と会話する。今回 Cursor 自身の AI 機能は使わない（あくまで「器」として使う）
Claude Code🧑‍💼 現場監督あなたの話し相手。相談・整理・小さな修正・文章作成を自分でこなし、重い作業は Codex に依頼して、返ってきた結果を自分で確認してから報告する
Codex CLI🔨 職人さんOpenAI のコーディングエージェント。Claude Code から codex exec というコマンドで仕事を受け、複数ファイルの実装・調査・テストなどを黙々とこなす

図に出てくる言葉

言葉ひとことで
サブエージェント監督の下で働く専門担当（記録係・相談役・Codex 窓口役など）。4章で説明
codex exec監督（Claude）が職人（Codex）に仕事を頼むときの合図（コマンド）
リファクタリング動きは変えずに、中身を整理し直すこと（部屋の配線をきれいに引き直すようなもの）
テストちゃんと動くかの確認
diff（ディフ）変更前と変更後の違い。どこが変わったかに色が付いて見える
ログプログラムが残す作業記録。エラーの手がかりになる
ポイント：あなたが直接 Codex に話しかける必要はありません。窓口は常に Claude Code。Codex の出力を Claude がそのまま転送することもしません（必ず中身を確認してから報告させる）。

  • それ以外の英字が出たら No。そして Claude に「これは何をするものですか？」と聞く
  • ファイルを書き換える確認なら、お願いした場所（ファイル名）なら Yes

階層場所書くこと

② プロジェクトプロジェクト/CLAUDE.mdそのプロジェクトの「事実」：概要、技術スタック、フォルダ構成、よく使うコマンド
③ プロジェクトの行動ルールプロジェクト/.claude/CLAUDE.mdそのプロジェクトでの「Claude の動き方」：Claude と Codex の担当の分け方、禁止事項など

4-3. サブエージェント ― 「役割分担」

サブエージェントは、特定の仕事だけを担当する Claude の分身です。~/.claude/agents/（全プロジェクト共通）または プロジェクト/.claude/agents/（そのプロジェクトだけ）に Markdown ファイルを1つ置くと使えるようになります。Claude に「〇〇役のサブエージェントを作って」と頼んで作ってもらうこともできます（ファイルを直接作っても同じです）。

  • 先頭の frontmatter（＝ ファイル先頭の --- で囲まれた設定部分）は name と description の2つだけでOK
  • description には「いつ呼ぶか」を書く。メインの Claude はファイルの本文ではなく、ここ（name と description）だけを見て呼び分ける
  • 本文は「役割」「チェック観点」「出力形式」の3節で十分

例1：レビュー役（~/.claude/agents/reviewer.md）

---
name: reviewer
description: Use before delivering any answer or code to the user. Final check for correctness, safety and completeness.
---

あなたは最終チェック担当。

## 役割
ユーザーに渡す前の回答・成果物を確認し、GO/NG を判定する。

## チェック観点
- 依頼された内容にすべて答えているか
- 事実や手順に誤りがないか
- 秘密情報が含まれていないか

## 出力形式
判定：GO / NG
指摘：（NGの理由と直し方）

例2：壊れパターン確認役（~/.claude/agents/tester.md）

---
name: tester
description: Use after implementation is complete to find edge cases and inputs that could break the feature.
---

あなたは壊れパターン確認担当。

## 役割
実装後のコードについて、壊れそうな使い方を洗い出し、実際に試せるものは試す。

## チェック観点
- 空の入力・巨大な入力・想定外の文字
- 二重クリック・連続実行
- ファイルが無い・ネットが切れている

## 出力形式
| パターン | 結果 | 対応要否 |
キットを使っている人が reviewer / tester を自作したら：キットの ~/.claude/CLAUDE.md には、<!-- と --> で囲まれた（＝コメントアウトされて効いていない）reviewer と tester の行が2か所あります。①「チーム構成」の表の下と、②「サブエージェントの呼び出し」の表の下です。両方とも、「（自分で決めた名前）」「（自分で決めたマーク）」などを書き換え、<!-- で始まる行から表の行（| で始まる行）の手前までの説明の行と、--> の行を消してください（表の行そのものは残します）。これで司令塔が2体をチームの一員として呼ぶようになります。
キャラクター設定は「続けるための味付け」：伏見さんの環境では、エージェントに名前・口調・担当カラーを付けています（例：レビュー役の「レビュアン」、Codex 窓口の「デックス」）。誰が何をしているか一目で分かり、使っていて楽しくなるので長続きします。ただし本質は「役割分担・記録・委任判断」の仕組みの方。キャラは慣れてから好きに足せばOKです。

6-3. codex exec の基本形

普段は窓口エージェントが実行するので、自分で打つ必要はありません。何をしているかの理解用です。

用途コマンドの形
読むだけの調査（まずはこれ）codex exec --sandbox read-only "依頼文"
ファイルを変更する作業codex exec --sandbox workspace-write "依頼文"
対象フォルダを指定codex exec -C 対象フォルダ --sandbox read-only "依頼文"
Git 管理外のフォルダで実行非推奨・使わない。--skip-git-repo-check を付けると動くが、前後を比べられず元にも戻せないため（6-5 参照）
# 例：調査だけ任せる
codex exec --sandbox read-only "src/ 以下でログイン処理を担当しているファイルと、その呼び出し関係を説明して。ファイルは変更しないこと。"
使わないオプション：--dangerously-bypass-approvals-and-sandbox（安全装置を全部外すもの）は使いません。
モデル名は推測しない：モデルを指定するときは、5章の「モデル名を設定する」で出した一覧にある名前だけを使います。一覧に無い名前を渡すと、エラーにならず意図しないモデルで動いてしまうことがあります。指定しなければ既定のモデルで動きます。

6-4. Codex の報告を鵜呑みにしない

Codex は「全部できました」「テスト通りました」と言うことがありますが、実際には一部しか直っていなかったり、頼んでいないファイルまで変えていたりすることがあります。必ず次で確かめます（窓口エージェントにやらせる）。

git status --untracked-files=all   # どのファイルが変わったか（新しく作られたファイルも全部出す）
git diff          # 具体的に何が変わったか
（プロジェクトのテストコマンド）   # 自分で実行して結果を見る
  • 頼んでいない範囲が変わっていたら、その部分は採用しない
  • 変更を採用したら、窓口エージェントが「基準を更新してよいですか」と確認してくるので、OKなら任せる（中で git add -A を実行して、今の状態を新しい「基準」として記録します）。更新しないと、次回の確認に今回の変更が混ざります
  • Codex が実装したコードも、Claude 側の実装と同じく壊れパターン確認 → 最終チェックを通してから受け取る
  • Codex が作業している間は、Claude 側で同じファイルを編集しない（同時編集禁止）

6-5. なぜ Codex に Git が必要なの？

結論：Git は「Codex に作業させる前と後で何が変わったかを比べて、ダメなら元に戻すための記録帳」です。GitHub（ネット上の置き場）とは別物で、Mac の中だけで動きます。

理由1：安全装置になっている

codex exec（Claude が Codex に仕事を頼むときのコマンド）は、Git 管理されていないフォルダだとエラーで止まって動きません。--skip-git-repo-check という指定を付ければ動きますが、変更前の状態を記録していないので、比べることも戻すこともできません。普段はGit 管理したフォルダで使うのが前提です。

理由2：何が変わったか正確に分かる

Codex は「直しました」と報告しますが、本当かどうかは分かりません。作業前を記録しておけば、git diff（変更前と変更後の違いを出すコマンド）で「どのファイルのどの行が変わったか」を出せます。窓口エージェントが Codex の報告をうのみにせず確認できるのは、このおかげです。

※ 新しく作られたファイルは git diff には出ないので、git status --untracked-files=all（新しいファイルも含めて、変わったファイルの一覧を出すコマンド）と合わせて確認します。

理由3：失敗したら戻せる

記録しておいた状態に戻せます。書き換えられたファイルは元に戻せます。ただし、新しく作られたファイルは別に消す必要があります。

たとえると

リフォームでいうとGit でいうと
📒 写真をしまうアルバムを用意するgit init
📷 工事前に部屋の写真を撮るgit add -A
🔍 工事後に写真と見比べるgit diff
↩️ ダメなら写真どおりに戻す元に戻す

写真がないと、職人の「ちゃんと直しました」を信じるしかありません。

あなたがやること
  • GitHub もコミット（変更を正式に保存する操作）も、覚えなくて大丈夫です
  • 練習用フォルダでは、3-6 で git init（記録帳を用意）、5-7 で git add -A（基準の写真を撮る）を、チャットで1回ずつお願いします
  • 実際の作業フォルダで git add -A が必要になったときは、Codex 窓口のエージェントが「記録してよいですか」と確認し、秘密のファイル（.env などのパスワードが入ったファイル）が混ざっていないかも確かめてくれます

付録. 伏見さんの上級設定（慣れてから）

最初は真似しないでください。ここに書いてあるのは、長く使って「何が起きるか」を分かったうえで入れている設定です。環境構築直後にこれを入れると、Claude や Codex が確認なしで何でも実行できる状態になり、事故のもとになります。また、伏見さんの settings ファイルはそのまま配りません（個人環境のフォルダ指定や、長年の「その場の許可」が千件単位で溜まっているため）。
設定何をしているか入れるなら
bypassPermissions
（settings.json の permissions.defaultMode）		コマンド実行・ファイル編集の確認プロンプトを出さない一番最後。確認プロンプトの意味が全部分かってから。「push 禁止」などは CLAUDE.md のルールだけで縛ることになる点を理解しておく
claude の alias（別名）に
--dangerously-skip-permissions		ターミナルから起動するときも確認なしで動かす上と同じ。初心者には非推奨
許可リスト
（permissions.allow）		よく使うコマンドを確認なしで許可する確認プロンプトで「今後も許可」を選ぶと自動で増える。自分で増やしていくもので、人のをコピーしない
hooks
（settings.json）		応答が終わったら Mac の通知を出す、などの自動処理「待ち時間に気づけない」と感じてから。外部送信しないものから始める
Codex の notify
（~/.codex/config.toml）		Codex の作業が終わるたびに外部プログラムを動かし、作業ログを記録するCodex 委任に慣れてから。最初は config.toml を触らなくてよい（codex login だけで動く）
サブエージェント10体＋キャラ設定調査・実装・テスト・レビュー・UI確認・Codex 窓口などを分業キットの3体＋4章の2体から始めて、必要になったら1体ずつ足す

ステップアップの目安

  1. 確認プロンプトの内容を読んで、自分で判断できるようになった
  2. よく使うコマンドだけ「今後も許可」にした
  3. Codex に読み取り専用の調査を任せ、結果を git diff とテストで確かめる流れに慣れた
  4. Codex に変更作業（workspace-write）を任せられるようになった
  5. その上で、通知フックなどの便利機能を足す
