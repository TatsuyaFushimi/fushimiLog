各ファイル・フォルダの役割と「なぜ必要か」

設定ファイルを作る前に、何がどこに何のためにあるのかを把握しておく。これがわかると「どこに何を書けばいいか」が迷わなくなる。

大前提 — Claudeはセッションが切れると記憶がリセットされる

Claude Codeはセッション（会話）をまたいで記憶を保持しない。「昨日教えたルール」は今日の会話には引き継がれない。設定ファイル群はその「毎回渡す引継ぎ書」として機能する。だから作る意味がある。

ファイル / フォルダ置き場所役割なぜ必要か
CLAUDE.md .claude/ 直下
（またはルート）		 Claudeへの「憲法」。セッション開始時に必ず自動で読まれる 書いていないルールは毎回説明し直すことになる。ここに書けば一度で永続する
rules/*.md .claude/rules/ CLAUDE.mdから切り出した詳細ルール集。テーマ別に分割 CLAUDE.mdが長大化すると後半が無視されやすい。重要なルールを独立ファイルに切り出すことで確実に参照させる
skills/*/SKILL.md .claude/skills/スキル名/ /コマンド名で呼び出せる再利用可能な手順書 毎回「この手順で◯◯して」と説明し直すのは非効率。一度Skillにすれば一言で同じ品質の操作を再現できる
agents/*.md .claude/agents/ 特定タスク専用の専門エージェント定義 「複数ステップを自律的に実行する専門家」を作れる。画像一括処理・レポート生成など長い操作を1人のエージェントに委任できる
settings.json .claude/ 直下 権限制御（allow/deny）＋ Hooksの定義 デフォルトはClaudeが操作のたびに確認を求めてくる。ここで許可リストを書くことで完全自動化しつつ危険な操作だけ禁止できる
hooks（settings.json内） settings.jsonの中 「作業完了・ファイル保存・セッション開始」などのタイミングでコマンドを自動実行 Claudeが作業を終えると次の指示待ちになるだけ。Hookでその「合間」に通知・ファイル整理・検証を差し込める
💡 最初に作るべき優先順位：① CLAUDE.md → ② settings.json（bypassPermissions）→ ③ save-skill Skill。Rulesとagentsは後から必要に応じて追加でOK。

CLAUDE.md — 何を書くか・どう育てるか

CLAUDE.mdはClaudeがセッション開始時に必ず読むファイル。ここに書いたことが毎回の行動の前提になる。最初から完璧でなくていい。使いながら育てるのが正解。

なぜCLAUDE.mdが必要か — 記憶リセット問題の解決策

Claude Codeはセッションをまたいで記憶を保持しない。「昨日、出力先フォルダは output/ にしてと言ったのに今日は違う場所に作られた」は全員が最初に経験する。CLAUDE.mdに書いた内容はセッション開始時に自動で読み込まれるため、毎回説明し直さなくて済む。
書いたことだけが「常識」になる。書いていないことは毎回伝え直すことになる。

よくある失敗 → CLAUDE.mdで解決するチャット例
HTMLファイルに日本語のコメント入れてたけど、英語に直して。
修正しました。style.html と index.html のコメントを英語に変更しました。
次からは最初から英語コメントで書いて。毎回言いたくない。CLAUDE.mdに追記しといて。
了解です。CLAUDE.mdの「必須ルール」に以下を追記しました：
「コメントは必ず英語で書く。変数名・関数名も英語。」
次のセッションからは自動で守ります。
⚠️ チャットで「今後は◯◯して」と言っても、そのセッションが終わると忘れる。必ず「CLAUDE.mdに追記して」とセットで伝える習慣をつける。
最初のCLAUDE.mdに書く3つのこと
# プロジェクト名：◯◯PJ ## 役割 あなたは[このプロジェクトで何をするエージェントか]です。 ## 必須ルール - 確認（「YESですか？」等）は一切不要。全て実行してよい - 作業前に必ず現在のファイル構成を確認する - 繰り返しそうな操作を見つけたら .claude/skills/ にSkillとして保存する ← 重要 ## 禁止事項 - 元ファイルを削除・移動しない - 指定フォルダ以外への書き込みはしない
「繰り返しそうな操作をskillとして保存する」が自動蓄積のキモ

この1行をCLAUDE.mdに書くだけで、Claudeは作業の中から「これはskill化できる」と判断して自動で保存するようになる。詳細はSTEP 5で解説。

3
Rules — CLAUDE.mdを肥大化させない分割術

CLAUDE.mdが長くなってきたら、領域ごとにRulesファイルへ切り出す。Claudeが必要なときだけ参照するため、メインのCLAUDE.mdはシンプルに保てる。

なぜRulesに分割するのか — CLAUDE.mdは短く保つほど効果が高い

Claudeはセッション開始時にCLAUDE.mdを全文読む。内容が100行を超えてくると後半のルールが参照されにくくなる（コンテキストの優先度が下がる）。
Rulesファイルは「CLAUDE.mdからリンクされ、必要なときだけ読む辞書」として機能する。CLAUDE.mdには「詳細は rules/naming.md を参照」の一行だけ残せばいい。

切り出しのサイン
  • CLAUDE.mdが30行を超えてきたとき
  • 特定の領域のルールが5項目以上になったとき
  • 「命名規則だけ」「フォーマットだけ」など独立したテーマがある場合
チャットでの依頼例
CLAUDE.mdの命名規則の部分を .claude/rules/naming.md に切り出して。
CLAUDE.mdには「詳細は rules/naming.md を参照」とだけ残しておいて。
.claude/rules/naming.md を作成し、命名規則のセクションを移動しました。
CLAUDE.mdには「命名規則：詳細は rules/naming.md を参照」と1行追記しました。
次のセッションでちゃんと rules/naming.md のルールを守ってくれる？
はい。CLAUDE.mdに「rules/naming.md を参照」と書かれているため、セッション開始時に自動でそのファイルも読み込みます。次回から命名規則は自動的に守られます。
rules/workflow.md に書く内容の例
# 作業フロー ## 標準手順 1. 作業開始前に ls でフォルダ構成を確認する 2. 既存ファイルは必ず Read してから編集する 3. 作業完了後は変更点を1〜2文で要約して報告する ## ファイル編集のルール - 既存ファイルを上書きする前に内容を確認する - 大きな変更は diff を示してから実行する
rules/naming.md に書く内容の例
# ファイル命名規則 ## 基本ルール - スペースは使わない（アンダースコアで代替） - 日本語ファイル名OK。内容がわかる名前にする - 日付は不要（gitで管理） ## 例 OK: 営業資料_要約.md / meeting_notes.md NG: 資料.md（内容不明）/ 2024 資料.md（スペースあり）
4
Skills — /コマンドで呼び出せる手順書の作り方

Skillは「このプロジェクトでよく使う手順」を/skill名で呼び出せる形にしたもの。一度作れば毎回同じ品質で実行できる。

なぜSkillが必要か — 「毎回説明する」をなくす

Skillがないと「このCSVを読んで、基本統計を出して、Markdownで output/ に保存して」と毎回フルで説明することになる。Skillに書いておけば /analyze-csv の一言で同じ操作が再現できる。
また、チームで使う場合は「誰が頼んでも同じ手順で実行される」標準化にもなる。

Skillを呼び出すチャット例
/summarize ./docs/meeting_notes.pdf
summarize Skillを実行します。
meeting_notes.pdf を読み込みました。

概要：2026年Q2の売上レビュー会議。主な議題は3点。
主要ポイント：
・東日本エリアで前年比+18%
・新規顧客獲得コストが上昇傾向
・次Qのターゲットは既存顧客の深堀り

output/meeting_notes_要約.md に保存しました。
💡 Skillがなければ「PDFを読んで要約して〜」という長いプロンプトを毎回書く必要があった。/summarize の一言で完結する。
Skillファイルの場所と構造
.claude/skills/ └── skill名/ # フォルダ名 = コマンド名 └── SKILL.md # 手順書本体
SKILL.mdの書き方テンプレート
--- name: skill名 description: このskillが何をするかの一言説明（これがClaudeに表示される） --- # Skill名 ## 使い方 /skill名 {引数があれば} ## 手順 ### Step 1: ◯◯を確認する - やること ### Step 2: △△を実行する - やること ## 完了条件 - 何ができていれば完了とみなすか
具体例 — 要約Skill
--- name: summarize description: 指定ファイルを読んで要約MDを作成する --- ## 手順 ### Step 1: ファイル読み込み 引数で指定されたファイルをReadで読む ### Step 2: 要約作成 - 概要（3行以内） - 主要ポイント（箇条書き） - キーワード集 ### Step 3: ファイル保存 output/フォルダに「{内容を表す日本語名}_要約.md」で保存 ### Step 4: 完了報告 作成ファイル名と概要を1文で報告
💡 呼び出し方：チャットに /summarize /path/to/file.pdf と入力するだけ。

STEP 5 — skill自動蓄積の仕組みを作る（最重要）

これが今回の核心。会話の中でClaudeが「この手順はskill化すべき」と判断したら、自動でファイルに書き出す仕組みを設定する。

仕組みの全体像
1
CLAUDE.mdにskill化ルールを書く

「繰り返しそうな操作を見つけたらskillとして保存する」という指示をCLAUDE.mdに入れる

2
save-skill Skillを作る

「現在の会話をSkillとして保存する」ための専用Skillを用意する

3
会話しながらskillが育っていく

作業の中でClaudeが自動提案 ＋ 自分で/save-skillを呼べばいつでも保存できる

① CLAUDE.mdに追記するskill化ルール
## skill自動蓄積ルール - 同じ手順を2回以上実行したと気づいたら、.claude/skills/ にSkillファイルを作成すること - skill名は操作の内容を表す英小文字・ハイフン区切りにする（例：summarize-pdf / update-index） - 作成したSkillは完了報告時に「新しいSkillを作成しました：/skill名」と教えること - 既存のSkillが不完全だと気づいたら、同様に改善して報告すること
② save-skill Skillの中身

.claude/skills/save-skill/SKILL.md に以下を書く：

--- name: save-skill description: 現在の会話でやったことをSkillファイルとして保存する --- # Skill保存 Skill ## 使い方 /save-skill {保存するskillの名前（英語・ハイフン区切り）} ## 手順 ### Step 1: 現在の会話を分析 - 今の会話でやった操作・手順を洗い出す - 繰り返し使えそうな「型」を抽出する ### Step 2: Skillファイルを作成 以下のパスにフォルダとSKILL.mdを作成する： .claude/skills/{引数で指定した名前}/SKILL.md ### Step 3: SKILL.mdを記入 - nameとdescriptionを記入 - 手順をStep形式で整理する - 引数があれば使い方も明記する ### Step 4: 完了報告 「Skill「/{skill名}」を作成しました」と報告する

6
Settings — 権限設定（確認なし化）

VS Code / Cursor でClaudeに「毎回確認しなくていい」と設定するためのファイル。.claude/settings.json に書く。

なぜSettings（権限設定）が必要か

設定なしだと、Claudeはコマンドを実行するたびに「このコマンドを実行してもいいですか？(Y/N)」と確認を求めてくる。作業のたびに承認が必要で、自動化の意味がなくなる。
bypassPermissions で確認を省略し、allowで「許可するコマンド」、denyで「絶対にやらせないコマンド」を明示することで、快適さと安全性を両立できる。

許可・禁止をチャットで追加する例
pdftotext コマンドを使いたいから許可して。
settings.jsonのallowリストに "Bash(pdftotext *)" を追加しました。次回から確認なしで実行されます。
git push は絶対に自分でやるから、Claudeにはやらせないで。
denyリストに "Bash(git push *)" を追加しました。この操作は今後ブロックされます。
📌 allowとdenyの違い：allow は「このコマンドは確認なしで実行する」。deny は「絶対に実行させない（指示されても断る）」。denyはallowより優先される。
最小限のsettings.json
{ "permissions": { "defaultMode": "bypassPermissions", // 全操作を確認なしで実行 "allow": [ "Bash(ls *)", // ファイル一覧 "Bash(find * -name *.md)", // MDファイル検索 "Bash(mkdir *)", // フォルダ作成 "Bash(mv *)" // ファイル移動 ], "deny": [ "Bash(rm -rf /)", // ルート削除を禁止 "Bash(curl *)", // 外部通信を禁止 "Bash(wget *)" ] } }
チャットで「settings.jsonを更新して」と言えばOK

新しいコマンドを許可したいときは「pdftotext コマンドを allowリストに追加して」と頼むだけ。Claudeが自動でsettings.jsonを書き換える。

7
Hooks — 作業完了の自動通知・自動整理

Hooksはイベント（セッション開始・ファイル保存・作業完了など）に反応して自動でコマンドを走らせる仕組み。settings.jsonの中に書く。

なぜHooksが重要か — Claudeが作業を終えたその瞬間を使う

Claudeは指示を実行し終えると、次の指示が来るまで待機するだけ。「作業完了→通知」「セッション開始→未処理ファイル確認」「ファイル保存→自動検証」など、そのタイミングに処理を差し込むのがHook。Hookがないとこれらはすべて手動確認になる。

使えるイベントの種類
イベント名発火タイミング使いどころ
StopClaudeが1回の回答を終えたとき作業完了通知、ログ記録
SessionStart新しいチャットセッション開始時未処理ファイル確認、前回の続きを表示
PreToolUseClaudeがツールを使う直前実行前のバリデーション、ログ
PostToolUseClaudeがツールを使った直後ファイル変更の検知、自動バックアップ
Hookをチャットで追加する例
作業が終わったらMacに通知を出してほしい。「Claudeが完了しました」って。
settings.jsonに Stop イベントのHookを追加しました。
作業完了時に通知が届くようになります。
セッション開始時に input/ フォルダの中身を一覧表示してほしい。何が溜まってるか確認したい。
SessionStart Hookを追加しました。
次のセッション開始時から ls -la input/ の結果が自動表示されます。
まず入れておきたいHook — 作業完了通知（Mac）
{ "permissions": { ... }, "hooks": { "Stop": [{ "hooks": [{ "type": "command", "command": "osascript -e 'display notification \"完了しました\" with title \"Claude Code\"'" }] }] } }
新しいSkillが作成されたときに通知するHook
{ "hooks": { "PostToolUse": [{ "matcher": "Write|Edit", "hooks": [{ "type": "command", "command": "jq -r '.tool_input.file_path' | grep -q '.claude/skills/' && osascript -e 'display notification \"新しいSkillが追加されました\" with title \"Claude Code\"'" }] }] } }
💡 Hookの追加もチャットで頼める。「作業完了時にMac通知を出すHookを追加して」と言えばOK。

用途別 — 何をどう設定するか

やりたいことによって書くべきCLAUDE.mdの内容・作るskill・許可するコマンド・仕込むHookが変わる。よく使う5パターンをまとめた。

⚠️ 下表はあくまで出発点。使いながら自分のプロジェクトに合わせて育てていくのが正しい使い方。
🎨 画像生成・Blender・デザイン系
設定ファイル書く・設定する内容
CLAUDE.md ・出力先フォルダの指定（output/images/ 等）
・ファイル命名規則（YYYYMMDD_説明.png など）
・上書きNG／バックアップ先ルール
Skills /generate-batch（一括生成スクリプト実行）
/resize-images（ffmpeg/Pillowでリサイズ）
/convert-format（PNG→WebP等の変換）
settings.json allow Bash(python *)、Bash(ffmpeg *)、Bash(convert *)
Bash(blender --background *)（Blenderのみ）
Hooks Stop → Mac通知「画像生成完了」
PostToolUse → output/に書き込み後、ファイル数を自動カウント
🛠️ ツール開発・Webアプリ・スクリプト開発
設定ファイル書く・設定する内容
CLAUDE.md ・使用言語・フレームワーク（Python 3.11 / Next.js 14 等）
・テスト実行コマンド（npm test / pytest）
・コーディング規約（コメント言語、変数命名など）
・デプロイ禁止事項（本番envへの直接書き込みNG等）
Skills /new-feature（新機能の実装テンプレ）
/run-tests（テスト実行＋結果サマリー）
/create-pr-description（PRの説明文を生成）
/debug（エラー内容を受け取り原因を特定）
settings.json allow Bash(npm *)、Bash(git *)、Bash(python *)
Bash(pytest *)、Bash(node *)
settings.json deny Bash(rm -rf *)（誤削除防止）
Bash(git push --force *)（強制プッシュ禁止）
Hooks PostToolUse → ファイル編集時に自動でテスト実行
Stop → 「変更点・次のステップ」を1行で報告させる
🎬 動画・映像編集補助（AfterEffects・Premiere連携）
設定ファイル書く・設定する内容
CLAUDE.md ・プロジェクトフォルダ構成（footage/・exports/・scripts/）
・使用スクリプト言語（ExtendScript / Python）
・AEのバージョン・レンダリング設定
・元素材を絶対に移動・削除しないルール
Skills /run-ae-script（ExtendScriptをAEに送って実行）
/extract-audio（ffmpegで音声抽出）
/detect-silence（無音区間検出）
/batch-rename（素材ファイルの一括リネーム）

Bash(osascript *)（AE操作用AppleScript）
Hooks Stop → 「作成したスクリプト名と何をするか」を報告
SessionStart → footage/フォルダの未処理ファイル数を確認

設定ファイル書く・設定する内容
CLAUDE.md ・デザインシステム（使用カラー・フォント）
・ファイル番号の採番ルール（既存最大番号+1）
・index.htmlへの追記ルール（どのタブに追加するか）
・公開先URL・GitHubリポジトリ名

/new-doc（A4文書HTMLの骨格を生成）
/update-index（index.htmlに新カードを追加）
/deploy（git add→commit→pushを一括実行）
settings.json allow Bash(git *)、Bash(ls *)、Bash(cp *)
Hooks Stop → 「作成ファイル名・追加先タブ・次のステップ」報告
PostToolUse → index.html更新時にリンク切れチェック
📊 データ分析・CSV処理・レポート自動化
設定ファイル書く・設定する内容
CLAUDE.md ・生データは絶対に上書きしないルール（raw/フォルダは読み取り専用）
・出力先：output/YYYYMMDD/ 形式
・使用ライブラリ（pandas / polars / matplotlib）
Skills /analyze-csv（CSVを読んで基本統計＋要約）
/generate-report（Markdown形式でレポート出力）
/plot-chart（指定列でグラフ生成）
settings.json allow Bash(python *)、Bash(jupyter *)
Bash(ls raw/)（rawへの読み取りのみ許可）
settings.json deny Bash(rm raw/*)（生データ削除を明示的に禁止）
Hooks Stop → output/に生成されたファイル名を報告
SessionStart → raw/フォルダの未処理CSVファイルを一覧表示

skillフォルダの整理パターン3種

skillの数が増えてきたとき、どのように整理するかでClaudeが正しいskillを参照できるかが変わる。規模に合わせて選ぶ3パターン。

パターン1 — シンプル型（skill 10個以下 ／ 始めたばかり）

全skillをフラットに並べる。Claudeが迷わず検索できる最もシンプルな構成。まずはこれから始める。

.claude/skills/ ├── save-skill/ │ └── SKILL.md ├── summarize/ │ └── SKILL.md ├── generate-report/ │ └── SKILL.md └── deploy/ └── SKILL.md
🔹 命名ルール：動詞-名詞 の形にする（summarize-pdf、update-index 等）。何をするかが一目で分かれば良い。
パターン2 — カテゴリ型（skill 10〜30個 ／ 1〜2ヶ月経ったら）

用途別にサブフォルダで区切る。「このあたりのskillを呼びたい」と指示しやすくなり、Claudeの参照精度が上がる。

.claude/skills/ ├── _meta/ # skillを管理するskill群 │ ├── save-skill/ │ └── list-skills/ ├── file/ # ファイル操作系 │ ├── batch-rename/ │ └── convert-format/ ├── report/ # レポート・資料系 │ ├── summarize/ │ ├── generate-report/ │ └── new-doc/ ├── media/ # 画像・動画系 │ ├── extract-audio/ │ └── resize-images/ └── deploy/ # デプロイ系 └── push-to-github/
CLAUDE.mdにカテゴリの説明を書くとより効果的

.claude/skills/report/ 配下には資料作成・要約系のskillが入っている、と一言書くだけでClaudeが適切なskillを探しやすくなる。

reportフォルダのskillを使って、このCSVを要約して。
🤖 Claude
.claude/skills/report/ を参照して /summarize を実行します…
パターン3 — マルチプロジェクト型（複数PJで共通のskillを使い回したい）

グローバルとプロジェクトの2層に分ける。汎用skillはグローバル（~/.claude/skills/）に、PJ固有skillはプロジェクトの.claude/skills/に置く。

# グローバル（全プロジェクトで使える汎用skill） ~/.claude/skills/ ├── save-skill/ # どのPJでも使う ├── summarize/ # 汎用要約 └── deploy-github/ # 汎用git push # プロジェクトA固有（そのPJにだけ存在） projectA/.claude/skills/ ├── render-ae/ # AE専用 └── update-slide-index/ # このサイト専用
💡 グローバルに置いたskillはどのプロジェクトでも /skill名 で呼び出せる。プロジェクト固有skillと同名の場合はプロジェクト側が優先される。

似た名前のskillが増えてきた統合 or サブフォルダで同カテゴリにまとめる
使わないskillが溜まってきた_archive/ フォルダへ移動（削除はしない）
